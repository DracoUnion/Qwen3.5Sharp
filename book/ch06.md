# 第 6 章 一次算一批：面板重打包与 panel GEMM

> 章节锚点源码：`src/Qwen35Sharp.Kernels/BlockLayout.cs`（`BlockQ4Kx8`/`BlockQ6Kx8`/`BlockQ2x8`/`BlockSTQ1_0x8`/`BlockQ8Kx4`）、`RepackQ4K.cs`（`MakeBlockX8`/`Rows`/`BuildMeta`）、`RepackQ6K.cs`（`Expand`/`MakeBlockX8`/`Rows`）、`RepackQ2.cs`（`Rows`）、`RepackSTQ.cs`（`Rows`）、`QuantizeQ8Kx4.cs`（`Quantize4x8`/`Quantize4x8FromRows`/`Quantize4x8Avx2`/`Quantize4x8Scalar`/`Quantize4x8Silu`）、`GemmQ4K.cs`/`GemmQ4K.Avx2.cs`（`Gemm8x8`/`GemmScalar`/`GemmAvx2`/`ColTileBytes`）、`GemmQ6K.cs`、`Q2Panel.cs`、`STQPanel.cs`、`MulMatPanel.cs`（`QuantizeAndGemm`/`SiluQuantizeAndGemm`/`PanelWeight`）、`MulMatQ2.cs`、`MulMatSTQ.cs`、`MulMatQ4K.cs`、`doc/04-quantization.md` §4.3–4.4、`doc/05-kernels.md` §5.1、§5.2、§5.6

第 5 章我们造出了 decode 的黄金路径，但它有个天然的软肋：一行一行算。而 prefill——也就是模型第一次吞下整段提示词的那一下——要一次消化几十甚至几百个 token。逐 token 跑 GEMV，会慢到让人无法接受。

所以这一章回答一个问题：**怎么把"一次一个 token"变成"一次一整批"？** 答案是一个贯穿 llama.cpp 生态、在本项目里被推到极致的思路：

> 把"位手术"（nibble 解包、scales 拆分、符号处理）从热循环里搬走，在加载期就把权重重排成"面板"并预解码尺度；这样，热循环里剩下的只有乘和加。

这就是"面板重打包 + panel GEMM"。它是全引擎性能上最重要的一次重构，也是理解后续一切调优的钥匙。

## 6.1 prefill 的痛点：为什么 GEMV 撑不起长提示词

先量化一下痛点。一次 prefill 要处理 `S` 个 token 的激活，形状是 `[S, nIn]`，要与权重 `[nOut, nIn]` 做矩阵乘法 `Y = X·Wᵀ`。如果用第 5 章的 GEMV 来算，就是 `S` 次独立的"一行输入 × 全部权重行"：

- 每次都要把全部 `nOut` 行权重从内存扫一遍（内存带宽消耗 = S 次全量扫描）。
- 每次只用一个 token 激活，SIMD 的并行度吃在"nIn 方向"上，但行的方向完全没并行。
- 每次进循环都要重新解一次 nibble/scales——位手术重复了 S 次。

`nIn` 动不动几千、`nOut` 动不动上万，一次 prefill 就是几千万次乘加。逐行 GEMV 在这个体量上，预填充时间会膨胀到用户无法等待。

于是 gl 面答案呼之欲出：**让矩阵乘在输出方向的 8 个列上并行**——一次处理 4 个 token、8 个输出列，把访存从"1 行激活 × 全部权重行"变成"4 行激活 × 8 列权重块"，权重只被扫 `S/4` 次。这个"4×8"的块度，是 llama.cpp 生态演化的自然选择，也是我们整套 panel 的形态。

## 6.2 重新排布世界的这一刻：panel 到底是什么

Panel（面板）是加载期构建的一种**内存布局变换**：把"8 个输出行"（在 GGUF 里是 8 条独立的行）的权重，按列交织重排成一个宽块。这样热循环只用一条 `vpbroadcast` 喂进一列激活，就能同时服务 8 列输出。

先看最典型的 Q4_K 面板 `BlockQ4Kx8`（1152 字节），它装的是 8 个 Q4_K 块（= 8 个输出列 × 256 K）的列交织：

```
D[8] u16     Dmin[8] u16     Scales[96]     Qs[1024]
```

- `Qs[1024]` 是关键的重排：它把 8 列 × 256 值交错存成 chunk。每个 chunk j（64 字节）含"列 0..7 × K 值 4j..4j+3"。于是热循环一条 `vpbroadcastq`（广播一个 64-bit 激活 chunk）就能喂 4 列——**一次广播，服务多个输出通道**。
- `Scales[96]`（8 列 × 12 字节）按"列"重排，让每列能找到自己的 scales。

但这还不是全部。Q4_K 最狠的一手是**预解码 meta**——`BlockQ4Kx8Meta`（448 字节）：

```
D[8] float    Dmin[8] float    Scales[192] short
```

这些不是一个字节一个字节搬，而是把"每列的 f32 D/Dmin 和 int16 的 scales/mins"在加载期就**算完存好**。存储顺序特意对齐 `vphaddw` 的输出顺序 `[c0 c0 c1 c1 c4 c4 c5 c5 | c2 c2 c3 c3 c6 c6 c7 c7]`，mins 交错 `[m0lo m0hi m1lo m1hi …]`。热循环的新玩法变成：**直接从 meta 数组 load f32，免去"反量化一遍"**。这是"位手术搬到加载期"的最纯粹形态。

把这些"重排"落到代码的是四个 `Repack*` 类，它们都有一个统一的形状 `Rows(源, 目标, nIn, nOut)`：

| 重打包器 | 输入 → 输出 | 要点 |
|----------|------------|------|
| `RepackQ4K.Rows` | `BlockQ4K` → `BlockQ4Kx8` | 8 列交织 nibble + scales 重排 |
| `RepackQ4K.BuildMeta` | `BlockQ4K` → `BlockQ4Kx8Meta` | 生成预解码 meta sidecar |
| `RepackQ6K.Rows` | `BlockQ6K` → `BlockQ6Kx8` | 展开为 u8 0..63 + scales/pairs 重排 |
| `RepackQ2.Rows` | `BlockQ2_0C` → `BlockQ2x8` | 拆 2-bit 码、跨列/跨 plane 重排 |
| `RepackSTQ.Rows` | `BlockSTQ1_0` → `BlockSTQ1_0x8` | 码本解码 → 0/1/2 的 2-bit panel |

它们都是**行序 → panel 序的纯拷贝重排**，发生在加载期、只读、只做一次，占模型加载时间的一小部分。此后，模型层的 GEMM 全部消费 panel，从不为热循环付位手术的税。

值得一提的对称设计：连**激活**也重排成 4 行的 panel（`BlockQ8Kx4`），这样"4 个 token"可以一次并行量化、一次喂给 GEMM。我们将在 6.3 讲它。

## 6.3 Q8_Kx4：把激活也排成 4 行的面板

`BlockQ8Kx4`（1168 字节）把 4 个 Q8_K 块（= 4 个 token 各 256 值）交织：

```
D[4] float    Qs[1024] sbyte    Bsums[64] short
```

- `Qs[1024]`：每 32 字节是 4 行 × 8 值。这样激活的"一条 32 字节"正好能被热量循环逐块加载，跟权重 panel 的 chunk 分形对齐。
- `Bsums[64]`：Q8_K 每块的 16 个 Bsums 也重排成 `((t>>2)<<4) + (t&3)` 顺序——这是 GEMM 读取 Bsums 时的索引模式。`QuantizeQ8Kx4` 用 `FillBsums` 做这个重排。

量化的并行化：`QuantizeQ8Kx4.Quantize4x8(float* x, BlockQ8Kx4* y, int k)` 一次并行量化 4 个 token。它有 AVX2 版和标量版（第 5.7 的纪律：SIMD 必有标量锚）。`Quantize4x8FromRows` 是参考实现。

还有一个为性能特供的融合版本 `Quantize4x8Silu(gate, up, y, k)`：**把 SiLU 的乘加算进量化循环里**。回忆 FFN 的公式 `ffn_down · silu(gate)⊙up`——gate 和 up 都要喂给同一个 GEMM，而 silu(gate)·up 这个乘积本来要单独算一遍再量化；融合版让"量化 up"的过程顺便把 `silu(gate)·up` 一起算进去，避免先写回 f32 再量化。这是"融合路径必须与朴素路径逐位守恒"的一次典型兑现：`FastExpTests.Quantize4x8Silu_MatchesSiLUThenQuantize` 单测断言两者逐字节一致。

## 6.4 4×8 GEMM：热循环只做乘加

一切重排都就绪了，现在看真正的热循环——`GemmQ4K.GemmAvx2`。它算 `C[4 tokens, 8 cols] += A[4, k] · Wᵀ[8, k]`（四组）。

我不打算贴整段代码，因为它的精髓是一家公司味十足的结构：

```
对每个 panel 节（8 列 × 一个 K-chunk）：
  // 激活侧
  v = vpbroadcastq( 激活行 chunk )          // 一次广播喂 4 列
  // 权重侧（完全来自预解码 meta）
  w_pairs = load( BlockQ4Kx8Meta.Scales )   // 已经是 int16 展开
  // 乘加
  acc = vpmaddubsw( w_pairs, v )            // 无 shuffle，纯乘加
  …用 adds / ands 累加…
```

为什么它能做到"无端口竞争"？秘密在指令选择：

- 激活用 `vpbroadcastq`——**纯加载指令**，只走 load 端口。
- 权重直接用 meta 里的 int16 scales——不需要任何 shuffle 端口去解位。
- 累加用 `vpmaddubsw`（乘加→int16）+ `vpmaddwd`（拓宽）——都吃 FMA/INT 管线。

于是每 8 个 `vpmaddubsw` 只配 8 次 adds、2 次 ands、6 次 loads，**没有任何 shuffle 端口工作**。这正是所有 SIMD 内核作者梦寐以求的形态：指令流不绕弯，管线喂得满。

Q6_K 的面板 GEMM（`GemmQ6K.Gemm8x8`/`GemmAvx2`）用上第 5 章埋的"−32 修正"：因为 Q6 展开成 u8 0..63（不是零中心 0..63−32 的 sbyte），所以点积累加的自然结果是 `Σ(sc·(q−32)·a)`，多出的一项 `−32·Σ(sc_i·bsum_i)` 被提出来、每 super-block 用一次 `ShiftLeftLogical(c, 5)`（×32 减）折叠进整数累加器——又是"重排+预计算把麻烦算进加载期"的一例。

Q2 与 STQ 的 panel GEMM（`Q2Panel.Gemm`/`STQPanel.Gemm`）一样是"一条 broadcast 喂多列"的结构，只是各自的面板排布不同（Q2 每 64B chunk 含列 0..7 × 8 字节、四个 2-bit plane；STQ 预解成 0/1/2 的 2-bit 面板）。它们的列序都会被 `Avx2.PermuteVar8x32(acc, ColumnOrder)` 修正成标准顺序——因为 `vpmaddubsw`/`vphadd` 通道天然产生 `[0 1 4 5 2 3 6 7]` 的列打乱，存储前必须修正回来。

## 6.5 一石二鸟：共享量化与三连乘

有一个性能点在做 GEMM 时几乎不会自己冒出来：**激活量化一次很贵，但 gate/up 或 q/k/v 都要用同一份激活。**

`MulMatPanel` 把"量化"与"GEMM"合并成一个协调动作：`QuantizeAndGemm` 在一个并行区段里，先量化一份 Q8 面板，再用自旋 barrier 同步，然后连续跑**至多三个** panel GEMM——它们共享同一份 Q8 面板：

```
MulMatPanel.QuantizeAndGemm(input, q8, nIn, tokens, pool,
                            w0,                // 第一个权重面板（如 ffn_gate）
                            w1 = default,     // 第二个（如 ffn_up）
                            w2 = default)     // 第三个可选（如 attn_q/k/v 的三投影）
```

`PanelWeight` 是个轻量 struct，把"面板指针 + 输出地址 + 输出行数"打包成一个可堆叠的参数（`ForQ4`/`ForQ6` 工厂方法）。这样调用层写起来很干净：`ffn_gate`/`ffn_up` 一次量化、两个 GEMM，或 `attn_q`/`attn_k`/`attn_v` 三个 GEMM 一次喂饱。

配合 `SiluQuantizeAndGemm`（把 silu(gate)·up 融进量化，第 6.3 提过），FFN 的两段（gate/up + down）在 prefill 里都吃上了共享量化 + 融合的福利。这是"性能设计六板斧"的第二斧，细节我们在性能章节会集中回顾。

## 6.6 调度路由：tokens==1 走 GEMV，否则走 GEMM

内核都齐了，但模型层需要的是一个**统一的路由**：同样一个线性层调用，decode 时该走 GEMV，prefill 时该走 GEMM。这就是 `MulMat*` 的统一入口。

以 `MulMatQ4K` 为例，它的派发逻辑非常直白：

```
Gemm(...):
  if (tokens == 1)  → GEMV 路径（QuantizeRow + 逐行点积）
  else              → prefill 路径（Quantize + panel GEMM）
```

但魔鬼在细节。`Gemv`/`Gemm` 要做三件容易被低估的杂务：

1. **`PackedGroups(nOut) = nOut / 8`**：把输出行切成 8 个一组的 panel 节；余下 `nOut % 8` 的尾部，用逐行 GEMV 补算（panel 面板要求 cols 是 8 的倍数）。
2. **token 数不是 4 的倍数**：`BlockQ8Kx4` 要求 4 个 token 一组。多出的 (tokens % 4) 个 token，补零到 4、算完再回拷有效部分或直接走逐行 GEMV。`MulMatQ4K` 内部处理这个"对齐"。
3. **`ScratchArena` 分配临时 Q8 缓冲**：用第 7 章将讲的竞技场，避免每次调用 new。

`GemvPrequant` 与 `GemmPrequant` 是另一种默契的 API：它接受调用方**已经量好的** Q8 行/面板（第 9 章 q/k/v 复用、第 5 章 DecodeGateUp 的通道）。这些预量化版本让模型层能"一次量化、两三次点积"，把内核的灵活性交给调用者。

> **一句话总结这一章**：prefill 慢的根源是逐行 GEMV 的重复解码与访存；解法是把权重重排成"8 列一页的面板"、把尺度预解码进 meta、把激活排成 4 行的面板，然后热循环退化为纯乘加；共享量化与三连乘进一步把"量化一次，喂多个矩阵"变成现实，`MulMat*` 的 `tokens==1` 路由则让同一个调用在 decode/prefill 之间无痛切换。但我们还欠着一个周期性问题——所有这一切，是在**多少线程**上、以**什么内存布局**运行的？——第 7 章，线程池、CPU 拓扑与内存竞技场。
