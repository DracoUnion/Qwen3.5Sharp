# 第 6 章 一次算一批：面板重打包与 panel GEMM

> 面向初学者：本章回答一个性能问题——"一次只处理一个 token 太慢，怎么让计算机一次处理 4 个？"。方法叫"面板重打包"（把权重提前摆成适合批量计算的形状）。每小节贴 `src/Qwen35Sharp.Kernels/` 的**真实源码**并配图。

第 5 章的 decode 路径有个软肋：一次只算一个 token。而 prefill（第一次读取整段提示词）要一次消化几十上百个 token。逐行 GEMV 会慢到让人无法接受。这一章的核心思想只有一句话：

> **把"繁琐的解码位运算"从热循环里搬走——在加载模型时就提前把权重摆成"面板"（panel），并预算出一切能预算的尺度；这样真正跑热循环的时候，只做最单纯的乘法和加法。**

这一章的走法：我们**首先**讲清 prefill 的痛点，为什么 GEMV 撑不起长提示词（6.1 节）；**其次**看"面板"到底是什么、怎么用 `Repack*` 在加载期重新排布世界（6.2 节）；**接着**把激活也排成 4 行的 Q8_Kx4 面板（6.3 节）；**然后**走进 4×8 的 GEMM 热循环（6.4 节）；**还**要学 `MulMatPanel` 怎么"一石二鸟"地共享量化（6.5 节）；**最后**看调度路由：一个 token 走 GEMV，一批 token 走 GEMM（6.6 节）。

## 6.1 prefill 的痛点：为什么 GEMV 撑不起长提示词

一次 prefill 要处理 `S` 个 token 的激活（形状 `[S, nIn]`），与权重（`[nOut, nIn]`）做 `Y = X·Wᵀ` 矩阵乘法。若用第 5 章的 GEMV，就是 `S` 次独立的"一行输入 × 全部权重行"：

- 每次都要把全体 `nOut` 行权重从头到尾扫一遍（内存带宽浪费 S 倍）；
- SIMD 的并行度只吃在 `nIn` 一个方向，行方向完全没并行；
- nibble / scales 的位手术重复做了 S 次。

于是解决方向呼之欲出：**在输出方向的 8 个列上并行——一次处理 4 个 token、8 个输出列**。这个 "4×8" 的块度，是 llama.cpp 生态长期演化出来的自然选择，也是我们整套面板的设计形态。

```mermaid
graph TD
    subgraph 一次 GEMV（慢）
        X1["1 个 token"] --> G1["所有权重行逐一点积"]
    end
    subgraph 一次 panel GEMM（快）
        X4["4 个 token 一排"] --> Q["4 行激活一起量化成 Q8_K×4 面板"]
        Q --> G4["权重面板一次喂 8 列输出<br/>4×8 一起算"]
    end
```

## 6.2 重新排布世界的这一刻：panel 到底是什么

Panel（面板）是加载期做的一次**内存布局重排**。原本 8 条独立的权重行，在内存里是"一行接一行"的顺序；面板则把它们**按列交织**排成一个宽块，这样热循环用一条"广播"指令，就能同时喂给 8 个输出列。

最典型的 Q4_K 面板 `BlockQ4Kx8`（`src/Qwen35Sharp.Kernels/BlockLayout.cs`，1152 字节 = 8 个 Q4_K 块）：

```csharp
[StructLayout(LayoutKind.Sequential, Pack = 1)]
public unsafe struct BlockQ4Kx8
{
    public fixed ushort D[8];        // 8 列各自的全局比例尺
    public fixed ushort Dmin[8];     // 8 列各自的全局最小值
    public fixed byte Scales[96];    // 8 列 × 12 字节 scales 重排（按列排）
    public fixed byte Qs[1024];      // 8 列 × 256 值列交织：
                                     //  chunk j(64B) = 列0..7 × K值 4j..4j+3
                                     //  一次 vpbroadcastq 喂 4 列
}
```

但 Q4_K 最狠的一手是**预解码 meta**——`BlockQ4Kx8Meta`（448 字节）：把每列的 f32 `D/Dmin` 和 int16 的 scales/min 提前算好存好，存储顺序特意对齐 `vphaddw` 的输出顺序。热循环从此不用解任何位：

```csharp
[StructLayout(LayoutKind.Sequential, Pack = 1)]
public unsafe struct BlockQ4Kx8Meta
{
    public fixed float D[8];          // 每列 f32 尺度，已解码
    public fixed float Dmin[8];       // 每列 f32 最小值，已解码
    public fixed short Scales[4 * 48]; // int16 scales/mins，按 vphaddw 输出顺序排列
}
```

落地这些重排的是四个 `Repack*` 类。`RepackQ4K`（`src/Qwen35Sharp.Kernels/RepackQ4K.cs`）的 `Rows` 一行接一行地把 8 行合成一个面板块：

```csharp
public static void Rows(BlockQ4K* src, BlockQ4Kx8* dst, int nIn, int nOut)
{
    int nb = nIn / Qk.SuperBlock;
    int groups = nOut / 8;
    BlockQ4K* tmp = stackalloc BlockQ4K[8];   // 临时攒 8 行
    for (int g = 0; g < groups; g++)
        for (int b = 0; b < nb; b++)
        {
            for (int r = 0; r < 8; r++) tmp[r] = src[(g * 8 + r) * nb + b];  // 取这 8 行的第 b 块
            MakeBlockX8(tmp, &dst[g * nb + b]);                             // 交错成一个面板块
        }
}
```

`BuildMeta` 负责生成侧边元数据（f32 D/Dmin + int16 scales，按内核要求的顺序）：

```csharp
public static void BuildMeta(BlockQ4K* src, BlockQ4Kx8Meta* dst, int nIn, int nOut)
{
    int nb = nIn / Qk.SuperBlock;
    ReadOnlySpan<byte> order = [0, 0, 1, 1, 4, 4, 5, 5, 2, 2, 3, 3, 6, 6, 7, 7]; // vphaddw 顺序
    // 对每个 panel 块：拆出 f32 D/Dmin；再对每对子块，按 order 摆好 int16 scales/mins
}
```

`RepackQ6K`（展开成 u8 0..63 + ScalePairs）、`RepackQ2`（拆 2-bit 跨列跨 plane 重排）、`RepackSTQ`（码本解码 → 0/1/2 面板）走同一条路——**加载期一次做掉，热循环从此免税**。

## 6.3 Q8_Kx4：把激活也排成 4 行的面板

权重摆好了，激活也得排成 4 行一组的形状。`BlockQ8Kx4`（1168 字节）把 4 个 Q8_K 块（= 4 个 token 各 256 值）交织：

```csharp
[StructLayout(LayoutKind.Sequential, Pack = 1)]
public unsafe struct BlockQ8Kx4
{
    public fixed float D[4];            // 4 个 token 各自的尺度
    public fixed sbyte Qs[Qk.SuperBlock * 4];  // 每 32 字节 = 4 行 × 8 值（与权重面板分形对齐）
    public fixed short Bsums[Qk.SuperBlock / 4]; // 重排成 ((t>>2)<<4)+(t&3) 顺序
}
```

`src/Qwen35Sharp.Kernels/QuantizeQ8Kx4.cs` 的 `Quantize4x8` 一次并行量化 4 个 token：

```csharp
public static void Quantize4x8(float* x, BlockQ8Kx4* y, int k)
{
    if (Avx2.IsSupported) Quantize4x8Avx2(x, y, k);   // 快速路径
    else                 Quantize4x8Scalar(x, y, k);  // 标量兜底
}
```

还有一个融合版本 `Quantize4x8Silu`——把 FFN 的 SiLU 乘加直接融进量化循环（避免先算 f32 再另量一次）：

```csharp
public static void Quantize4x8Silu(float* gate, float* up, BlockQ8Kx4* y, int k)
{
    float* tmp = stackalloc float[4 * Qk.SuperBlock];
    int nb = k / Qk.SuperBlock;
    for (int i = 0; i < nb; i++)
    {
        for (int row = 0; row < 4; row++)
            SiluMulBlock(gate + row * k + i * Qk.SuperBlock,   // silu(gate)·up
                         up + row * k + i * Qk.SuperBlock, tmp + row * Qk.SuperBlock);
        Quantize4x8(tmp, y + i, Qk.SuperBlock);
    }
}
```

## 6.4 4×8 GEMM：热循环只做乘加

一切重排就绪，看热循环——`src/Qwen35Sharp.Kernels/GemmQ4K.Avx2.cs` 的 `GemmAvx2`：

```csharp
public static int ColTileBytes = 128 * 1024;   // 列方向 L2 分块字节数（保持权重切片在 L2 缓存）

public static void GemmAvx2(int n, float* dst, int ldc, BlockQ4Kx8* weights,
    BlockQ8Kx4* activations, int rows, int cols, BlockQ4Kx8Meta* meta)
{
    int nb = n / Qk.SuperBlock;
    int tileGroups = Math.Max(1, ColTileBytes / (nb * Qk.Q4Kx8Size));  // 一次放多少列组进 L2
    int groups = cols / 8;
    for (int g0 = 0; g0 < groups; g0 += tileGroups)                    // 按列块推进
        GemmAvx2Tile(n, dst + g0 * 8, ldc, weights + g0 * nb, activations,
                     rows, Math.Min(tileGroups, groups - g0) * 8, meta + g0 * nb);
}
```

内部 `GemmAvx2Tile` 对每个 panel 节、每个激活行：`vpbroadcastq`（纯加载）对着**原始列交织 nibble** 做 `vpmaddubsw`（乘加）——每 8 个乘加只配 8 adds、2 ands、6 loads，**没有任何 shuffle 端口工作**。列序 `[0 1 4 5 2 3 6 7]` 在存储时用一次 `PermuteVar8x32` 修正。scales 直接从 meta load（已解码，零位手术）。

`GemmQ6K`（`GemmQ6K.cs`）的"−32 修正"——因为 Q6 展开成 u8 0..63（不是中心化后），所以点积结果多出一项 `−32·Σ(sc_i·bsum_i)`，把它整体提出、每 super-block 用一次移位指令折进累加器：

```csharp
j0 = Avx2.Subtract(j0, Avx2.ShiftLeftLogical(c0, 5));   // ×32 减，一次搞定 −32 修正
```

`Q2Panel`/`STQPanel` 同样是"一条广播喂多列"，各自列序都在存储前 `PermuteVar8x32(acc, ColumnOrder)` 修复：

```csharp
private static Vector256<int> ColumnOrder => Vector256.Create(0, 1, 4, 5, 2, 3, 6, 7);
// ... Gemv 收尾：
Avx.Store(dst, Avx2.PermuteVar8x32(acc, ColumnOrder));   // 修正 vphaddd 打乱的列序
```

## 6.5 一石二鸟：共享量化与三连乘

`src/Qwen35Sharp.Kernels/MulMatPanel.cs` 把"量化"与"GEMM"合并成一个协调动作——**一个并行区段里，先量化一份 Q8 面板，自旋 barrier 同步，再连续跑至多三个面板 GEMM**。这样 gate/up（甚至 q/k/v）共享同一份量化好的激活：

```csharp
public unsafe struct PanelWeight
{
    public BlockQ4Kx8* Q4;  public BlockQ4Kx8Meta* Meta;
    public BlockQ6Kx8* Q6;  public float* Dst;  public int NOut;
    public static PanelWeight ForQ4(...) => new() { Q4 = packed, Meta = meta, Dst = dst, NOut = nOut };
    public static PanelWeight ForQ6(...) => new() { Q6 = packed, Dst = dst, NOut = nOut };
}

public static void QuantizeAndGemm(float* input, BlockQ8Kx4* q8, int nIn, int tokens,
    CpuThreadPool? pool, PanelWeight w0, PanelWeight w1 = default, PanelWeight w2 = default)
{
    int nb = nIn / Qk.SuperBlock;
    int quantGroups = tokens / 4;
    pool?.For(Math.Max(quantGroups, w0.NOut / 8), (worker, workers) =>
    {
        int g0 = quantGroups * worker / workers, g1 = quantGroups * (worker + 1) / workers;
        for (int g = g0; g < g1; g++)
            QuantizeQ8Kx4.Quantize4x8(input + g * 4 * nIn, q8 + g * nb, nIn);   // ①先量化
        pool.Barrier();                                                          // ②同步
        GemmRange(w0, q8, nIn, tokens, worker, workers, nb);                     // ③连续 GEMM
        GemmRange(w1, q8, nIn, tokens, worker, workers, nb);
        GemmRange(w2, q8, nIn, tokens, worker, workers, nb);
    });
}
```

`SiluQuantizeAndGemm` 是 ffn_down 的融合版（silu(gate)·up 融进量化再一锤 GEMM）。Q2 的对应物在 `MulMatQ2.QuantizeAndGemm`/`SiluQuantizeAndGemm`。

## 6.6 调度路由：tokens==1 走 GEMV，否则走 GEMM

`MulMatQ4K.Gemm` 统一入口（真实代码，三件被低估的杂务都注释出来）：

```csharp
public static void Gemm(BlockQ4Kx8* packed, BlockQ4K* rows, float* input, float* output,
    int nIn, int nOut, int tokens, CpuThreadPool? pool = null,
    ScratchArena? scratch = null, BlockQ4Kx8Meta* meta = null)
{
    if (tokens == 1) { Gemv(rows, input, output, nIn, nOut, pool, scratch); return; }   // 路由到 GEMV

    int paddedTokens = (tokens + 3) & ~3;   // ① token 数补到 4 的倍数（不够就补零、算完回拷）
    int packedCols = nOut & ~7;             // ② 输出列补到 8 的倍数（主体走面板）
    // ...对齐/补零、scratch 分配、QuantizeAndGemmPrequant...
    // ③ packedCols..nOut 的尾部列用逐行 Dot 补算：
    for (int row = packedCols; row < nOut; row++)
        dst[t * nOut + row] = VecDotQ4K.Dot(rows + row * nb, q8row, nIn);
    // ...未对齐时回拷到 output...
}
```

主线（`QuantizeAndGemmPrequant`）是 llama.cpp `mul_mat` 的精确移植：`pool.For` 一个并行区段 → 量化组 → `pool.Barrier()` → GEMM 组。`GemvPrequant`/`GemmPrequant` 接受**已量好**的 Q8 行/面板（第 9 章 q/k/v 复用通道）。

> **一句话总结这一章**：prefill 慢的根源是逐行 GEMV 的重复解码与访存；解法是把权重重排成 8 列面板（`RepackQ4K.Rows`/`BuildMeta`、`RepackQ6K`/`RepackQ2`/`RepackSTQ`）、激活排成 4 行面板（`QuantizeQ8Kx4.Quantize4x8`/`Quantize4x8Silu`），热循环退化为纯乘加（`GemmQ4K.GemmAvx2`、`GemmQ6K`、`Q2Panel`/`STQPanel`）；`MulMatPanel.QuantizeAndGemm` 实现共享量化 + 三连乘。但这一切跑在**多少线程**、什么**内存布局**上？——第 7 章，线程池、CPU 拓扑与内存竞技场。
