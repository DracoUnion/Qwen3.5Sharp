# 第 12 章 稀疏 FFN：只算被选中的专家

> 章节锚点源码：`src/Qwen35Sharp.Model/Qwen35Model.Moe.cs`（`PrefillSparseMoe`/`DecodeSparseMoe`/`TopKSoftmax`/`ExpertGateUp`/`ExpertDown`/`ExpertBase`）、`Qwen35Model.cs`（`Weight.ExpertStride`）、`doc/08-moe.md`

第 11 章我们把"四层里三层的线性注意力"填完了。模型骨架里还剩下最后一块个性化部件：FFN。dense 模型的 FFN 在第 9 章已经会算了（gate/up 共享 Q8 + SiluQuantizeAndGemm）；本章补上 `qwen35moe` 变体——**稀疏 MoE（Mixture-of-Experts）**。它的核心命题是：与其让所有 token 都走同一个巨大的 FFN，不如准备几百个"专家"，每个 token 只让 top-k 个专家干活。

## 12.1 MoE 的数学与一次计算的全流程

先看 MoE 层的数学。它替换掉的只是一个 FFN，但计算路径完全不同：

```
router_logits = x @ ffn_gate_inpᵀ              # [tokens, num_experts]
probs = softmax(router_logits)
top-k 索引与权重 → 重归一化，让 top-k 权重和为 1
out = Σ_k expert_weight_k · Expert_k( silu(gate_k(x)) · up_k(x) )
shared = sigmoid(x @ ffn_gate_inp_shexpᵀ) · SharedFFN(x)     # 若存在共享专家
out += shared
```

一次完整的 MoE 前向（拿 `PrefillSparseMoe` 作例子）包含四步：

1. **路由打分**：`Linear(ffn_gate_inp, x) → routerLogits[rows, experts]`——一个 `[tokens, numExperts]` 的矩阵。名字 `gate_inp` 值得注意：这把矩阵的"行"是 token、"列"是专家，它是"谁该被哪个专家处理"的裁判。
2. **softmax + top-k**：对每个 token（行）整行 softmax 得到概率分布，再选 top-k 个专家（`TopKSoftmax`）。
3. **逐 token 逐专家**：对每个 token 的每个被选中专家，算 `silu(gate_k(x))·up_k(x)`，向下投影，再按专家权重加权累加。
4. **共享专家**：若模型带共享专家（`ffn_gate_shexp` 等存在），算一个共享 FFN，并按 sigmoid 门控（`sharedGateLogit`）加起来。

MoE 的收益来源，用一句话说透：**把 "token × 巨大 FFN" 变成 "token × 少数专家的小 FFN + 一个便宜的路由器"**。Qwen3.5 MoE 有 256 个专家，每 token 只激活 8 个——计算量是"全专家都算"的 8/256 ≈ 1/32。这个稀疏性，是 MoE 在相同 FLOPs 下塞进更多参数的原因。

两个必须刻进脑子的正确性要点（也是容易写错的两步）：

- **top-k 重归一化发生在 softmax 之后**。不能先归一化、再砍到 top-k，而要先选 top-k、再把它们的权重比例缩放到和为 1（`Σw=1`）。顺序错了，加权和就偏离真实期望。
- **共享专家与主 MoE 的相加顺序**与参考实现一致——shared 的部分是加到加权专家输出上的，顺序不能颠倒（顺序只影响浮点尾差，但既然我们对拍，就不能有自己的顺序偏好）。

## 12.2 3D 专家张量：一个张量装下全员

我们说过（第 8 章）MoE 的专家权重是 3D 张量，加载期不重打包。现在把它讲透。

`ffn_gate_exps.weight` / `ffn_up_exps.weight` 的形状是 `[hidden, moeFfn, numExperts]`，`ffn_down_exps.weight` 是 `[moeFfn, hidden, numExperts]`。注意**专家在第三维**。这意味着全员的 gate 权重在**一个张量**里，按专家沿第三维排列。

`Weight` 里的两个字段，是专门为它准备的：

```
NExpert
ExpertStride = nOut · nb · blockBytes      // 专家之间的字节步长
```

为什么记录字节步长而不是"按 NOut 线性估计"？因为 3D 张量 `[nIn, nOut, experts]` 的专家沿第三维切片，切片间距是"一个专家完整的一块数据"的大小，即 `nOut · nb · blockBytes`（nOut 行 × 每行的块数 × 每块字节）。直接按这个步长索引，是定位第 exp 个专家切片的正确方式。`ExpertBase(w, exp) = base + exp · ExpertStride` 就干这个：

```csharp
private static byte* ExpertBase(Weight w, int exp)
    => w.Q4 + (long)exp * w.ExpertStride;   // 或对应其它类型的基址
```

**为什么加载期不重打包成 panel？** 因为 MoE 在 decode 阶段只做逐专家 GEMV，且每次只激活 top-k 个专家。panel 是为"8 列一起喂"的 GEMM 服务的；逐专家 GEMV 的输入是单 token、输出是小矩阵，panel 的收益被"每次只碰 8 个专家"稀释掉了。这是一个"重打包的 ROI 由使用模式决定"的决策——用到第 16 章的"性能设计"视角。

## 12.3 路由：TopKSoftmax 与共享专家门控

### TopKSoftmax：朴素但有效的贪心 top-k

`TopKSoftmax(logits, rows, nExperts, nUsed, indices, weights)` 做三步：

```
对每行：
  1) 整行 softmax：先减 max（数值稳定）、exp、归一
  2) 贪心选 top-k：简单线性扫描 nUsed 次
     每次找到当前最大，记录 index，把它置为 -1（排除，防重复选中）
  3) 把选中的 weights 重归一化为和 1
```

"置 −1 排除"这个技巧很朴素——它把"找前 k 大"变成 k 次线性扫描，每个 O(nExperts)。对 `nUsed ≤ 8` 的典型场景，完全够用，不需要堆/分区选择排序。代码读取时注意 `indices`/`weights` 是输出参数（预分配的 int*/float*），`TopKSoftmax` 不分配任何托管数组。

**为什么"重归一化在 softmax 之后"？** 因为 softmax 的分布已经把专家间的关系（相对权重）编码好了；top-k 之后再 re-scale，保证相对比例不变、总和为 1。若在 softmax 前先做 top-k（比如直接取 logits 最大 8 个再 softmax），得到的分布其实也正确，但与参考实现的"先 softmax 再 top-k 再 renormalize"数值上不完全一致。我们对拍，所以照参考来。

### 共享专家的门控

共享专家（shared expert）是 MoE 里"每个 token 都算"的那一部分——专门捕捉"所有 token 都需要的公共变换"，避免 top-k 太随机导致主专家忽略公共推理。

它的两样器（`PrefillSparseMoe` 的共享段）：

```
sharedGateLogit[token] = F32Gemm(ffn_gate_inp_shexp, x)   # 每行一个标量
shared = Linear(ffn_gate_shexp, x) → SiLUMul → Linear(ffn_down_shexp)    # 一遍共享 FFN
out += sigmoid(sharedGateLogit) · shared
```

两个边界值得记：

- `ffn_gate_inp_shexp.weight` 形状是 `[hidden, 1]`（每 token 一个标量 logit）——所以 `F32Gemm` 一行一个标量输出。用它做 sigmoid 门控，决定 shared FFN 的输出以多大比例加进主输出。
- 注意**判断共享专家存在**的标准：`ffn_gate_shexp.weight` 这个张量存在。若 `MoeSharedCount >= 1`，就有共享专家。整段共享计算包在 `if` 里，缺了就直接跳过。

## 12.4 逐专家 GEMV 与性能取舍

MoE 的 decode（`DecodeSparseMoe`）与 prefill（`PrefillSparseMoe`）完全同构，只是 `rows=1`。它们的生命周期是：

```
对每个 token r：
   TopKSoftmax(router, r) → 选中的 (exp_k, weight_k)
   output[r] = 0
   for k in top-k:
     (gate, up) = ExpertGateUp(x[r], layer, exp_k)
                  # 两个 GEMV：gate = ffn_gate_exps[:, :, exp_k] · x
                  #          up  = ffn_up_exps[:, :, exp_k]     · x
     o = SiLUMul(gate, up)
     down = ExpertDown(o, layer, exp_k)      # ffn_down_exps[:, :, exp_k] · o
     output[r] += weight_k · down
   # 共享专家（若存在）… output[r] += sigmoid(...) · shared
```

`ExpertGateUp` 与 `ExpertDown` 是这一节的"心脏"，它们用 `ExpertBase(w, exp)` 拿到专家切片，然后走 `DecodeLinear`（单 token 的 GEMV）。

### 一个诚实的性能注脚

第 11 章我们为线性注意力的标量循环道过歉；MoE 也要坦白两点：

1. **每次 GEMV 独立量化**。`ExpertGateUp` 内部对 x 做的 Q8 量化（`IQ4XS.Gemv`/`Q5K.Gemv`/`MulMatQ4K.Gemv`）每次独立做——同一行 x 被 top-k 个专家各量化一次。显式优化方向是"一次量化、top-k 次点积"（`GemvPrequant` 路线），只是当前为正确性优先还没合并。
2. **逐 token 逐专家串行**。`PrefillSparseMoe` 对每一行、每一个选中的专家做 GEMV，无法复用 Q8 面板。优化方向是"同一专家被多个 token 选中时合并成 panel GEMM"——把那组 token 的 Q8 面板一次性打包，一次 GEMM 服务多个 token。这是 MoE 当前最重要的热点，也写在 `doc/08-moe.md` §8.5 与 `doc/12-limitations.md` 的未来工作里。

这两点不是缺陷，是"先算对"留下的迭代空间。MoE 的收益来自 `只算 8/256` 这个分母；把分母变小的各种 GEMM 合并技巧，是我们迭代它的全部空间。

### `ExpertWeightsScale` 的一个待办

`ModelConfig.ExpertWeightsScale` 已从 GGUF 读入，但当前**未应用**到专家输出（如果 `qwen35moe` 需要乘法缩放，需在 `output[r] += w·down` 处乘 `expert_weights_scale`）。它出现在"已知限制"章节——这是"诚实清单"的一部分：读出来了、但实现尚未消费。读者若在自己的复刻里遇到专家输出偏大/偏小，这里是第一个要检查的地方。

## 12.5 章末：把骨架的最后一格填上

到本章为止，模型层的全部个性化部件都齐了：

- **全注意力层**（第 10 章）：标准 GQA + RoPE + per-head norm + sigmoid 门控。
- **Gated-DeltaNet 层**（第 11 章）：卷积 + β/α 递推 + 门控 RMSNorm + 输出投影。
- **FFN**（第 9 章 dense + 本章 MoE）：dense 走共享 Q8 的 gate/up/down；MoE 走"router → top-k → 逐专家 GEMV → shared 专家"。

第 9 章立起的统一层画布上，三块肉都填完了。模型层可以完整地跑：`Forward` 的每个分支都指向真实的代码，全注意力、线性注意力、FFN 三条路由都成立，缓存与状态都正确更新。

但这是"引擎"的"模型层"完整了——还差模型层之外的最后一公里：**文字怎么进出**。token 是引擎的语言，但用户说的是中文英文；聊天模板决定消息怎么组织。第 13 章，我们让文字进得去、出得来。

> **一句话总结这一章**：MoE 用"router 打分 → softmax → top-k → 逐专家 GEMV → 共享专家"把巨大 FFN 变成"只算被选中的 8/256"，3D 专家张量用 `ExpertStride` 按第三维切片；目前逐专家独立量化与串行 GEMV 是已知热点，未来方向是"同专家多 token 合并成 panel GEMM"。至此模型骨架填满——接下来的问题不再是"模型层怎么算"，而是"用户怎么看见"。
