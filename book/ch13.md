# 第 13 章 让文字进得去出得来：字节级 BPE 与聊天模板

> 章节锚点源码：`src/Qwen35Sharp.Model/BpeTokenizer.cs`（`BpeTokenizer`/构造函数/`Encode`/`Decode`/`DecodeVisible`/`IsStop`/`Bpe`/`ByteEncode`/`EncodeByte`/`AppendTokenBytes`）、`ChatTemplate.cs`（`RenderQwen35`/`ChatMessage`）、`doc/09-tokenizer-cli.md`

模型的四层引擎都齐了——token 进、logits 出。但用户接触到的永远是最外围两层：**文字↔token** 的分词器，与"怎么组织输入消息"的聊天模板。这一章把引擎从"数学机器"变成"能受理中文对话的程序"，而且全程由 GGUF 的 `tokenizer.ggml.*` 元数据驱动，不依赖任何外部库。

## 13.1 预拆分特殊 token：别让 `<|assistant|>` 被 BPE 撕碎

先看最容易被忽视、却最容易让输出变成垃圾的一步。

字节级 BPE 的合并规则是学来的（来自训练时的词频统计）。它对普通文字很有效，但对**特殊 token** 很致命——因为特殊 token（如 `<|system|>`、`<|assistant|>`、`<|endoftext|>`）在训练语料里以"完整 token"出现，BPE 合并很可能把它们拆成碎片（`<|ass` + `istant|>` 之类）。而模型在训练时是**把特殊 token 当作一整块**看待的——你把它的碎片喂给模型，等于输入了训练时从没见过的序列。

解决方法是显式预拆分，`BpeTokenizer` 的构造函数先做两件事：

1. 从元数据收集特殊 id 集合 `_specialIds`：
   - `tokenizer.ggml.token_type` 中类型为 {3, 4} 的 token（模型定义的特殊 token）；
   - 以及等于 `bos_token_id` / `eos_token_id` 的 id。
2. `Encode(text)` 开头，把已知特殊 token 的字符串从原文里**先切出来**，其余片段继续做 BPE。

看 `Encode` 的前半段：它维护一个 `fragments` 列表，每个元素是 `(text, presetIds)`。最初它是 `[(text, null)]`（整段待处理）。然后对每个特殊 token，反复 `IndexOf` 找它在片段的哪里出现：找到就把 `[起点..idx)` 切成普通片段、`[idx..idx+len)` 切成带预设 id 的特殊片段——逐步把特殊 token 全部分离出来。

这个"预切特殊 token"的收益巨大且几乎不可见：没有它，多轮对话里 `<|assistant|>` 这个"turn 边界"就会碎，整个对话结构错乱。它是一个"用户不道谢但输出一定感谢"的细节。

`_specialIds` 用 `HashSet<int>` 收纳，查重 O(1)。`TryLookup` 提供"按 token 字符串反查 id"的辅助（`DecodeVisible` 流式输出的基础）。

## 13.2 预分词与字节编码：一统中文与英文

特殊 token 切走后，剩下的普通文本按三小步进入 BPE 管道。

### 预分词：正则把句子切成词素

`ResolvePreTokenizer` 返回那个著名的 Qwen/GPT-2 风格正则：

```
's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+
```

解读它：

- `'s|'t|'re|'ve|'m|'ll|'d`——英文缩写的词素。
- ` ?\p{L}+`——字母序列（可带前导空格）；` ?\p{N}+`——数字序列。
- ` ?[^\s\p{L}\p{N}]+`——其它非空白、非字母数字的字符串。
- `\s+(?!\S)|\s+`——空白（含"后跟非空白"的回车等）。

` ?` 前缀保留"空格归属"——一个"前面带一个空格的词"是一个词素，这正是 BPE 里"单词间空格"能被合并进 token 的物理基础。`Encode` 对每个普通片段跑 `_pretokenizer.Matches(frag)` 得到词素序列。

### 字节编码：把 UTF-8 字节映射到可打印字符

`Bpe` 合并的工作介质是"字符"，而我们要喂给它的词素是任意 UTF-8 文本（中文、emoji……）。不能直接喂 Unicode 码位——因为同一字符的字节编码在不同 token 里会不一致（BPE 是按**字节**学的）。所以 `ByteEncode` 把每个词素的 UTF-8 **字节**逐一映射到"可见字符区间"：

```
EncodeByte(byte b):
  b == 0xAD            → 0x0143
  b <= 0x20            → b + 0x100        # 控制符挪到高位区，可打印
  0x7F <= b <= 0xA0    → b + 0xA2         # DEL/Range 挪开
  else                 → b                # 普通 ASCII/字节原位
```

比如隐藏的空格字节 0x20 → 0x0120（一个看似 Unicode 的字符）。这样每个字节"住进"一个可打印字符单元，BPE 的合并就对纯字符序列操作，不必担心字节/代码位错位。这套"字节↔字符"双射是 GPT-2/字节级 BPE 的祖传手艺，`BpeTokenizer` 原样实现。

### BPE 合并：从单字符到词素

`Bpe(token)` 拿到一个词素，先按字符拆成单元素 `word` 列表，然后反复合并：

```
while word.Count > 1:
  best = +∞; bestIndex = -1
  for i in 0..word.Count-2:
    rank = _merges[ word[i] + " " + word[i+1] ]     # 查合并表 "a b" → rank
    if rank < best: best = rank; bestIndex = i
  if bestIndex < 0: break                            # 没有任何可合并对
  word[bestIndex] += word[bestIndex+1]               # 合并
  word.RemoveAt(bestIndex+1)
```

`_merges` 是一个 `Dictionary<string,int>`：键是 `"a b"`（空格夹两个相邻元素），值是训练时给它的 rank。每次找 rank 最小的相邻对合并，直至无可合并。合并表由 `tokenizer.ggml.merges` 按序构建——**rank 即数组下标**，这正是"越靠前越应该先合"的 BPE 语义。

最后把 `word` 里的每段查 `_tokenToId` 得到 token id；找不到（不明词素）回退 `UnkId`——这就是未知 token 的兜底。

注意 `Encode` 里还有个"整词素直查"的快路径：`ByteEncode` 后若 `_tokenToId.TryGetValue(normalized, out id)` 直接命中，就不进 `Bpe` 合并了（词素本身就是完整 token）。这是对"常见词都是单一 token"这一事实的廉价优化。

## 13.3 Decode 与增量流式：把 id 还原成可显示的文字

解码是编码的逆过程，`Decode(ids)`：

```
bytes = 空缓冲
for id in ids:
  if (uint)id >= (uint)_idToToken.Length: continue     # 越界 id 跳过
  AppendTokenBytes(_idToToken[id], bytes)              # token → 原始字节
return Encoding.UTF8.GetString(bytes)                  # 字节 → 文本
```

`AppendTokenBytes` 是 `ByteEncode` 的逆映射：把"住进字符区"的字节映射回原始字节（0x0120→0x20、0x0143→0xAD、区间 0x0121..0x0142→0x7F..0xA0+…），普通 <0x100 的字符原样进，否则丢给 `Encoding.UTF8.GetBytes`. 最后用 `Encoding.UTF8.GetString` 把字节串还原成文本。

`DecodeVisible` 即 `Decode`——但它的**存在意义**在 CLI 的流式输出（第 14 章）。流式时，我们每步只 decode 增量（新生成的几个 token），需要把"已可见部分"缓存住，每次追加打印"新可见部分"——`DecodeVisible` 就是那个稳定的"可见文本基准"。

停止判定 `IsStop(id) = id == EosId || id < 0`：Qwen3.5 的生成以 `eos_token_id`（对应 `<|endoftext|>`/`</s>`）作为停止条件。CLI 每步 `if (model.IsStop(token)) break`。注意这里 `id < 0` 是防御——某些 token id 可能是负的（越界），碰到直接停，避免死循环。

## 13.4 Qwen3.5 聊天模板：把消息拼成模型期待的格式

训练时模型看到的消息格式是固定模板，推理时我们必须复刻它——否则模型对"规则"一无所知。`ChatTemplate.RenderQwen35(messages, addGenerationPrompt, enableThinking)` 就是这个复刻。

`ChatMessage` 是个简单的 `readonly record struct (string Role, string Content)`——角色与内容。`RenderQwen35` 按角色一个个拼：

```
system   → <|system|>\n{content}\n<|/system|>\n
user     → <|user|>\n{content.Trim()}\n<|/user|>\n
assistant→ <|assistant|>\n{content}<|/assistant|>\n      # 不 Trim！
生成提示 → <|assistant|>\n thinking\n
         （enableThinking=false）→ <|assistant|>\n thinking\n\n response\n\n   # 空思考块
```

三个细节值得品味：

1. **user 要 Trim，assistant 不 Trim**。用户消息往往带多余空白，`Trim()` 干净；但 assistant 内容（模型自己生成的输出）必须**原样保留**——因为多轮对话里，渲染历史时 assistant 的每一字都要忠实，不能因为它自带首尾空白就被吞掉，否则下一轮模型看到的上下文与训练时的格式产生偏差。这是一个"写代码时最容易想当然、错起来最难排查"的细节。
2. **生成提示是 `<|assistant|>\n thinking\n`**：模型一看到 `<|assistant|>` 就开了一个"assistant turn"，紧跟的 ` thinking` 让它在思考块里输出推理。`enableThinking=false` 时它会**先结掉思考块**（`</think>` 等价物）再给 `\n\n response\n\n`——即显式"不思考，直接回答"。
3. **模板是纯文本**：`ChatTemplate` 没有视觉/多模态占位。模型本身单模态，模板也单模态。如果读者未来要接 Qwen3.5 的视觉模型，这里才是第一个要加东西的地方。

CLI 每次多轮对话，把历史 `messages` 重新 `RenderQwen35` 成提示词，再 `Tokenizer.Encode`——"历史即上下文"。这也是为什么 `KvCacheAlign`（第 10 章）要做前缀复用：每轮提示词都变长，但**前缀每次都一样**（system + 之前所有轮次），所以能命中缓存。

> **一句话总结这一章**：`BpeTokenizer` 用特殊 token 预拆分、预分词正则、字节编码、BPE 合并，把文字可靠地编成 token id、再可靠地 decode 回来；`ChatTemplate` 把消息按 Qwen3.5 的模板拼成 `<|system|>/<|user|>/<|assistant|>` 结构并加生成提示。文字这一头通了。现在只剩最后一件事：把一切都装进一个能交互的程序里，让模型真正开口说话——第 14 章，CLI 与自回归生成循环。
