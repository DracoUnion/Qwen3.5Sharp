# 第 17 章 这台引擎的边界，以及它还能走向哪

> 章节锚点源码：`doc/12-limitations.md`、`README.md`（"尚未实现"节）、`doc/11-performance.md` §11.6、`doc/08-moe.md` §8.5、`doc/03-gguf.md` §3.4

任何诚实的工程书，都要在结尾给读者一张"地图的空白处"。这一章回答三个问题：哪些能力是我们**刻意不实现**的（非目标），哪些是**已知的工程取舍**（约束与雷区），以及——最重要的——如果读者想继续往前走，该往哪个方向依次投入（路线图）。

## 17.1 明确的非目标：哪些能力刻意不实现

先看一张表，把"我们没做什么"一次说清：

| 能力 | 现状 | 一句话说明 |
|------|------|-----------|
| 视觉 / 多模态 | 不支持 | 无 `Qwen3_5VisionModel`、无 3D 位置 id、无 M-RoPE 分段；`ModelConfig.RopeDim` 是部分旋转的 1 维 RoPE 维度 |
| 投机解码 / MTP | 不支持 | Multi-Token Prediction 是性能加速器，非正确性必需品 |
| 分块 Gated-DeltaNet | 只做顺序递推 | 顺序与分块数学等价，分块仅为长序列 prefill 的内存优化 |
| 采样器多样性 | 仅贪心 argmax | CLI 无 top-k / top-p / 温度 |
| KV 量化 | 无 | KV 缓存为 f32；f16/i8 可省 decode 带宽（带宽受限嘛） |

其中"分块 Gated-DeltaNet"值得多说一句，因为它最容易让人误解为功能缺失。第 11 章讲过，顺序递推与分块递推**数学等价**：都是同一个 delta rule，只是分块把一批 token 的实现排布得更有缓存亲和。llama.cpp 的逐 token decode 走的也是顺序递推。所以"只做顺序递推"不是"没做完"，而是"正确的实现 + 一条明确的内存优化路线"。真正会动到的东西，是 `GatedDeltaNetOps` 的调用形态与状态布局，不是数学本身。

为什么刻意不做视觉/多模态？因为"从零自制"这本书的射程，是证明"文本推理的完整因果链"；视觉引入的 M-RoPE 分段（多模态位置编码）会大幅增加实现面积，而收益是另一个完整的故事。把这几样标进"非目标"，是为了让读者明确知道雷达的边界，而不是以为雷达坏了。

## 17.2 已知限制：能跑，但别在这些边上踩雷

工程现实总有取舍。以下是六条"知道就不踩雷"的约束，每条都解释"为什么是"与"怎么绕"。

### 1. 热路径依赖 AVX2+FMA

最硬的一条。热路径（GEMM/GEMV/Softmax）要求 `Avx2.IsSupported && Fma.IsSupported`；Q2/STQ 的 panel 路径在无 AVX2 时抛 `PlatformNotSupportedException`（其余格式有标量回退）。无 AArch64/NEON 路径。

- **为什么**：内核全部手写在 AVX2 上，为旧 CPU 保留标量回退是"正确（慢）"的兜底，但 panel 路径的整套优化（第 6 章）在无 AVX2 时失去意义，直接拒绝比"假装能跑"诚实。
- **怎么绕**：在现代 x86 上运行；未来加 NEON 是明确方向（17.3）。

### 2. `token_embd` / 量化张量的 `nIn` 必须是 256 的倍数

`LoadWeights` 检查这一点。绝大多数 GGUF 量化权重满足（256 是 super-block 的天然倍数），但 embedding 层若 inner dim 非 256 会被拒绝加载。

- **为什么**：量化块以 256 值为单位，`nIn` 非 256 的倍数意味着"没整块"的部分无法用标准块路径处理。
- **怎么绕**：此约束由模型发布方天然满足；对极端特例模型，需要先 pad 或走 F32 fallback。

### 3. 只有 `nOut >= 8` 且 `nExpert == 1` 的 Q4_K/Q6_K/Q2_0C/STQ1_0 才重打包

第 8 章 `LoadWeights` 的重打包条件。其余走 GEMV 尾部或逐行点积。

- **为什么**：panel 是"8 列一页"的布局，`nOut < 8` 或 3D 专家张量（`nExpert != 1`）用 GEMV 更简单正确。
- **怎么绕**：对特定 layer 用 panel、其余用 GEMV——这个混合本项目已经天然支持（`MulMat*` 的路由）。

### 4. STQ1_0 兼容标记有条件

早期 HyMT2 Stride16 文件需 raw type 42 + file_type 41 + 名称含 `Stride16` 才被识别为 STQ 并规范化；否则按标准 Q2_0 解释（第 3.6 节）。

- **为什么**：type 42 歧义的历史根源（第 3.6），只能靠特征消歧。
- **怎么绕**：新文件不要用 type 42 存 STQ；老文件保持特征字段不变。

### 5. 前缀缓存截断不影响线性层

`TruncateCache`（第 10/14 章）只回滚全注意力 KV；线性层状态在对话中只增不减，只有 `/reset`（`ResetCache`）全清。多轮对话中发生"回退重写"时线性层状态可能不与 KV 同步。

- **为什么**：线性状态 S/卷积窗口压缩在固定矩阵里，无逐位置可回滚结构（第 11.7）。
- **怎么绕**：约束对话形态（缓存只增，/reset 才清）——本项目采用的正是这条"诚实的约定"。

### 6. `EnsureScratch` 用启发式估算

若 MoE/线性层维度组合超出估算，`Bump` 抛 `InsufficientMemoryException`（已给出提示信息；需更新估算公式）。

- **为什么**：`EnsureScratch` 的"最坏单层占用估算 + 4MB 余量"是启发式（第 8.4），碰到极端组合可能不够。
- **怎么绕**：更新的类，按异常提示重算估算公式；这是"已知的改进点"而非"未修复的 bug"。

把这六条当作"运行守则"而非"缺陷清单"，你会发现自己早能熟练地绕开它们。

## 17.3 未来路线：从这本书出发，能走向哪里

最后，把地图的空白处铺成一条**可依序行走的路线**。这里按"低垂果实 → 工程中期 → 长远愿景"分三层，每层都指向具体的源码位置——你不是要从零探索，只是沿着已知的路标往前走。

### 第一层：低垂果实（不动架构的优化）

1. **MoE 批处理**（`Qwen35Model.Moe.cs`）：把"同一专家、多个 token"的 GEMV 合并成 panel GEMM；共享专家已用 GEMM（`PrefillSparseMoe` 的 shared 段）。这是 MoE 最热的热点，ROI 最高。
2. **Gated-DeltaNet 就地归一化**（`GatedDeltaNetOps.cs`）：L2 归一化免去每 token 的 `float[]` 分配。
3. **向量化三 pass**（`DeltaStep`）：把 kvMem/read/write 三条标量循环改 AVX2——以 `GatedDeltaNetOpsTests` 为不破门槛。
4. **prefill 插桩补全**（`Ticks*`）：让剖面覆盖 prefill 的 conv/recurrence，优化就有了"看见"。

### 第二层：工程中期（动内存布局的优化）

5. **分块复现（chunk）**：为长序列 prefill 降低数组尺寸——改的是 `RecurrentGatedDeltaRule` 的调用形态，数学不变。
6. **KV 量化（f16/i8）**：给 KV 缓存加量化/反量化内核，decode 带宽受限的现状（第 16.4）就松绑了。
7. **更多量化类型读入**：Q3_K、TQ/TQ2、BF16；Q5_K/IQ4_XS/STQ1_0 的 prefill panel GEMM（第 6 章表格留的白）。
8. **端到端测试与基准**：加入一个小公开 GGUF 做生成冒烟 + tok/s 基准，补上第 15.6 的盲区 1。

### 第三层：长远愿景（把引擎推向更多人）

9. **ARM64 / NEON 路径**：为 AArch64 .NET 提供 NEON/SVE 内核回退——从"x86 专属"变成"全平台"。
10. **CLI 采样丰富**：top-k/top-p/温度、`--seed`、KV 状态导出。
11. **投机解码 / MTP**：把第 2 章"非目标"里的大件拉回来——那又是一本书的深度。

### 一个收尾的呼告

还记得第 1 章我们开的工吗？四个回合：文件回合、计算回合、模型回合、用户回合。现在，四个回合都走完了，引擎在终端里说话，测试锁住了它的正确性，剖析看见了它的时间，边界画出了它的地图。

但"从零自制"从来不是终点，而是**让读者有能力继续往里挖**的起点。这本书给你的，不是一份成品源码的复印件，而是一条"我亲手把一坨权重字节变成一句人话"的完整路径，和一路上所有值得停下来思考的岔路口。当你合上这本书，捡起任何一份未来的模型权重、任何一台新 CPU、任何一条新的架构路线时，你会知道从哪儿看起、先查什么、怎么验证、往哪儿优化——这正是我们写下它的全部意义。

> **全书写到这里，最后一句话送给读者**：自制引擎最重要的产出，不是那个能对话的程序，而是在建造它的过程中，你亲手建立起来的、关于"计算是如何真正发生"的直觉力。愿这本书成为你直觉的垫脚石。
