# 第 16 章 性能剖析：看见时间都去哪了

> 章节锚点源码：`src/Qwen35Sharp.Model/Qwen35Model.cs`（`ProfileEnabled`/`ResetProfile`/`Ticks*` 静态计数器）、`doc/11-performance.md`、`doc/02-architecture.md` §2.4-D7、`doc/04-quantization.md` §4.3、`doc/08-moe.md` §8.5

"算得对"之后，"算得快"就是下一座山。而性能优化的第一步永远不是优化，而是——**看见**。谁在慢？哪个算子吃了最多时间？哪一层从第几层开始数值不佳？这一章把项目的剖析手段、诊断开关与已知瓶颈原样整理，教读者"先定位，再优化"。

## 16.1 内建剖析计数器：算子级耗时的秒表

第 5–12 章里，我们反复在各种算子旁埋"计时探针"。现在把它们收拢成一整套：`Qwen35Model` 的静态计数器。

```
ProfileEnabled（静态 bool，开启剖析）
TicksQ4   TicksQ2   TicksSTQ   TicksQ6   ← 各类型权重的 GEMM/GEMV 耗时
TicksAttnScore TicksSoftmax TicksAttnCombine   ← 注意力三段式
TicksRms TicksRope TicksSilu TicksEmbed       ← 逐点算子
TicksDelta TicksConv                          ← Gated-DeltaNet 递推与卷积
```

用法极其简单：开启 `ProfileEnabled = true`，decode/attention 路径上每个算子用 `Stopwatch.GetTimestamp()` 包裹、把差值累加到对应计数器；跑几轮后 `ResetProfile()` 清零，再把累计值除以 `Stopwatch.Frequency`，就得到"占时间最大的算子"分布：

```
TicksQ4 / TicksQ2 / …  / TicksAttnScore / … / TicksDelta / …
```

这是"算子级剖面"——比看总耗时有用得多，因为它直接告诉你**下一刀该砍哪里**。

三个诚实注脚（写在真代码旁边，读者跟着看会认路）：

1. **`Ticks*` 是 `static long`**——刻意做成静态，因为剖析是诊断期的事，不该为生产代码引入对象状态。
2. **部分计数器只在 decode 路径累积**（`TicksRope`/`TicksDelta`）；prefill 路径还未全部插桩。所以用剖面做`decode`针对性优化时可信，做 prefill 时要注意盲区。
3. **`ResetProfile()` 清零**是跑多轮前必做的——否则旧轮累积会污染"本轮分布"。

这就是项目"性能设计"里"诊断与剖析内建"那条的落地。

## 16.2 追踪与诊断：Q35_TRACE 与 Q35_DIAG

除了耗时秒表，还有两个用于**定位"哪里错了"**的环境变量。它们不是剖析计数器，而是手术探针。

### Q35_TRACE=1：逐层逐子步骤的进入/完成跟踪

设置 `Q35_TRACE=1`，每次前向会在 stderr 打逐层逐子步骤的日志：

```
attn_norm 进入/完成
gemm q … / conv … / recurrence … / moe … / ffn_down …   （每层每步都留痕）
```

这是"程序化白盒"——哪层卡住、哪一步没跑、哪个 buffer 没就位，一眼可见。对"前向流程本身有 bug"的排障极有用。

### Q35_DIAG=1：逐层隐藏态范数诊断

设置 `Q35_DIAG=1`，每 3 层打印最后一 token 隐藏态的 RMS 范数（归一化到 /hidden 的 `|h|`），前向末尾打印整体 `|h|` 与 `|normed|`。

这工具专治一个典型的灾难：**数值发散**。训练好的模型，任意层的隐藏态范数应该稳定在一定范围；如果某层某处（比如 Gated-DeltaNet 的递推，第 11 章）开始指数爆炸，`|h|` 会在那一层突然飞飙。`Q35_DIAG` 把"哪层开始炸"直接打出来——配合第 11 章的"先查 L2 归一化 / 衰减越界"清单，能迅速缩小嫌疑到具体那个算子。

**一个诊断实例的工作流**（本书想让读者掌握的"惯例"）：

```
症状：输出乱码、重复 token
1. Q35_DIAG=1 跑一次短输入 → 看 |h| 从哪层开始偏离正常范围
2. Q35_TRACE=1 同输入 → 确认那层哪些子步骤被触发
3. 针对可疑区（如某头 delta 递推）设断点/加临时对拍 → 定位到函数
4. 修 → 重跑 Q35_DIAG → |h| 恢复正常
```

这套"剖面 + 追踪 + 范数诊断"的三件套，是作者在真实调试里打磨出的组合拳。

## 16.3 性能设计的全景回顾：六板斧

到现在为止，全书散落的性能决策已经攒出**一套成体系的设计哲学**。第 12/15 章分别预告过"性能设计六板斧"，这里收束成一张全景表，每条回指成形的章节，让读者能形成自己的优化决策框架：

| # | 板斧 | 成形的章节 | 一句话 |
|---|------|-----------|--------|
| 1 | **加载期重打包** | 6.2、4.3 | 位手术搬到加载期，热循环只做乘加 |
| 2 | **decode/prefill 分流** | 5.1、6.1 | GEMV 服务单 token，GEMM 服务整批 |
| 3 | **共享激活量化** | 5.2、6.5、9.4 | 一次量化喂多个矩阵（q/k/v、gate/up） |
| 4 | **L2 列分块** | 6.4 | 权重切片驻留 L2，q8 行流式扫过 |
| 5 | **拓扑感知线程** | 7.1、7.2 | 物理 P-core 数 + job-id 轮询 + 自旋 barrier |
| 6 | **标量回退兜底** | 5.7、7.2 | 无 AVX2 时正确（慢），热路径总是 SIMD |

这六板斧不是互相独立的窍门，而是一个"栈"：内存布局（斧 1）→ 计算形态（斧 2/3）→ 缓存利用（斧 4）→ 并行与基础（斧 5/6）。当你遇到一个新瓶颈，先从最底层斧子找起。

## 16.4 已知瓶颈与优化路线

最后，把"我们已经知道慢、但还没修"的地方如实列出。这些不是羞辱，是**路线图**——本书停在"正确"的岸上，把"更快"的地图留给读者。

### 1. MoE prefill：逐专家独立量化，未批处理

`PrefillSparseMoe`（第 12 章）对每个被选中专家的 GEMV 各做独立 Q8 量化，逐 token 逐专家串行。

**怎么优化**：同一专家被多个 token 选中时，把那组 token 合并成 panel GEMM（一次量化、一次 GEMM 服务多个 token）。这是 MoE 当前最大的热点，方向明确、收益可测。

### 2. Gated-DeltaNet 递推：托管数组分配 + 标量三 pass

`RecurrentGatedDeltaRule`/`DeltaStep`（第 11 章）每 token 分配 `float[] qN/kN` 做 L2 归一化，`DeltaStep` 里 kvMem/read/write 三 pass 是标量循环。

**怎么优化**：就地 L2 归一化（免去每次分配）；向量化三 pass；可选分块（chunk）复现以降低长序列 prefill 的数组大小。全部以 `GatedDeltaNetOpsTests`（第 15.2）为不改正確性的守门。

### 3. prefill 部分路径未插桩

第 16.1 提过：`Ticks*` 主要覆盖 decode；prefill 的 conv/recurrence 未单独计。

**怎么优化**：补插桩。优化的前提是剖面的完整性——没有"看见"，就没有"改对"。

### 4. Q5_K / IQ4_XS / STQ1_0 prefill：退化为逐 token GEMV

这几类格式没做 panel GEMM（第 6.2 的表里只有 Q4_K/Q6_K/Q2_0C/STQ1_0 有 panel）。

**怎么优化**：为它们补 panel GEMM。Q5_K 尤其适合——它的 prefill 目前几乎是"最慢的可用格式"。

### 5. softmax 的 FastExp：每元素一条分支

`SoftmaxCausal`（第 10.3）里 `FastExp` 每元素一条分支；批量路径已向量化，但分支仍在。

**怎么优化**：把"减 max + floor(−80) + 掩码"拆成无分支的向量操作。

### 6. KV 缓存是 f32：decode 带宽偏高

KV 缓存（第 8.4）是 f32。decode 是带宽受限的，f32 KV 读走带宽多。

**怎么优化**：做 f16/i8 KV 缓存 + 量化/反量化内核。这是"decode 提速"的一条高回报路线，代价是实现复杂度。

这些路线图合起来说明一件事：**这本书的"性能完结"是一块故意留下的画布**。我们没有说完最后一句话，是因为"从零自制"的意义不在一份完美的成品，而在一套能让你自己继续优化的能力——现在你知道了六板斧，知道了三件套探针，知道了优化路线图的形状。剩下的，是你的路。
